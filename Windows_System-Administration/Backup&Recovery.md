**Backup** ნიშნავს მონაცემების დამატებითი ასლის შექმნას, რათა მათი აღდგენა შესაძლებელი იყოს დაკარგვის, დაზიანების, შემთხვევით წაშლის ან სხვა პრობლემის შემთხვევაში. მაგალითად, თუ კომპიუტერში მნიშვნელოვანი დოკუმენტები, ფოტოები ან სამუშაო ფაილები გაქვს, მათი ერთადერთი ასლის მხოლოდ კომპიუტერში შენახვა სარისკოა. თუ დისკი გაფუჭდა, ransomware-მა ფაილები დაშიფრა ან მომხმარებელმა შემთხვევით წაშალა მონაცემები, შეიძლება ყველაფერი დაიკარგოს.

Backup-ის მთავარი იდეა არის **ორიგინალი მონაცემებისგან დამოუკიდებელი ასლის არსებობა**. თუ Backup იმავე დისკზე ინახება, სადაც ორიგინალი ფაილებია, დისკის გაფუჭების შემთხვევაში ორივე შეიძლება დაიკარგოს. ამიტომ მნიშვნელოვანი მონაცემებისთვის გამოიყენება სხვა დისკი, გარე საცავი, NAS ან Cloud Storage.

Backup-ის რამდენიმე გავრცელებული ტიპი არსებობს. **Full Backup** აკეთებს არჩეული მონაცემების სრულ ასლს. მისი აღდგენა შედარებით მარტივია, რადგან ყველაფერი ერთ Backup-შია, თუმცა მეტი დრო და საცავი სჭირდება.

**Incremental Backup** ინახავს მხოლოდ იმ ცვლილებებს, რომლებიც ბოლო Backup-ის შემდეგ მოხდა. მაგალითად, თუ ორშაბათს Full Backup გაკეთდა და სამშაბათს რამდენიმე ფაილი შეიცვალა, სამშაბათის Incremental Backup მხოლოდ ამ ცვლილებებს შეინახავს. შემდეგ დღეს ისევ მხოლოდ ახალი ცვლილებები დაემატება. ეს მეთოდი ნაკლებ სივრცესა და დროს მოითხოვს, თუმცა სრული აღდგენისას შეიძლება რამდენიმე Backup-ის გამოყენება გახდეს საჭირო.

**Differential Backup** ასევე მხოლოდ ცვლილებებს ინახავს, მაგრამ ითვლის მათ ბოლო Full Backup-თან შედარებით. მაგალითად, თუ ორშაბათს Full Backup გაკეთდა, სამშაბათს შეიცვალა 2 ფაილი, ოთხშაბათს კიდევ 3, ოთხშაბათის Differential Backup უკვე ყველა ცვლილებას შეიცავს ორშაბათის Full Backup-თან შედარებით.

Backup-ის სისტემის დაგეგმვისას მნიშვნელოვანია **3-2-1 Backup Rule**. იდეა ასეთია: მონაცემების უნდა არსებობდეს მინიმუმ **3 ასლი**, რომლებიც ინახება მინიმუმ **2 განსხვავებულ ტიპის საცავზე**, და მინიმუმ **1 ასლი უნდა იყოს სხვა ადგილას ან Off-site**. მაგალითად, ორიგინალი კომპიუტერში, Backup გარე დისკზე და კიდევ ერთი ასლი Cloud-ში. ამ მიდგომით ერთი მოწყობილობის გაფუჭება ან ერთი ტიპის პრობლემის წარმოქმნა ნაკლებად იწვევს მონაცემების სრულ დაკარგვას.

Backup-ის არსებობა ჯერ კიდევ არ ნიშნავს, რომ მონაცემები აუცილებლად აღდგება. ამიტომ აუცილებელია **Restore-ის ტესტირებაც**. თუ Backup შექმენი, მაგრამ არასდროს შეგიმოწმებია მისი აღდგენა, შეიძლება საჭირო მომენტში აღმოაჩინო, რომ ფაილები დაზიანებულია ან Backup არასრულად შეიქმნა. პროფესიონალურ გარემოში Backup-ის პერიოდული შემოწმება და Restore Test მნიშვნელოვანი პრაქტიკაა.

**Recovery** უფრო ფართო ცნებაა და გულისხმობს სისტემის ან მონაცემების პრობლემის შემდეგ სამუშაო მდგომარეობაში დაბრუნებას. მაგალითად, შეიძლება საჭირო გახდეს შემთხვევით წაშლილი ფაილის აღდგენა, დაზიანებული Windows-ის აღდგენა ან მთლიანად კომპიუტერის Backup-იდან აღდგენა.

Windows-ში არსებობს **System Restore**, რომელიც სისტემის გარკვეული მდგომარეობის წინა მდგომარეობაზე დაბრუნებაში გვეხმარება. ის შეიძლება სასარგებლო იყოს მაშინ, როდესაც მაგალითად ახალი დრაივერის, პროგრამის ან სისტემური ცვლილების შემდეგ Windows-ში პრობლემა წარმოიქმნა. System Restore ძირითადად სისტემურ კონფიგურაციასა და შესაბამის კომპონენტებს ეხება და არ უნდა მივიჩნიოთ მომხმარებლის ყველა პირადი ფაილის სრულ Backup-ად.

არსებობს ასევე **Windows Recovery Environment (WinRE)** — სპეციალური აღდგენის გარემო, რომელიც გამოიყენება მაშინ, როდესაც Windows ჩვეულებრივ რეჟიმში ვერ იტვირთება. WinRE-დან შესაძლებელია სხვადასხვა Recovery ინსტრუმენტის გამოყენება, მაგალითად Startup Repair, System Restore ან სხვა პრობლემის მოგვარების საშუალებები.

თუ პრობლემა იმდენად სერიოზულია, რომ Windows-ის აღდგენა ჩვეულებრივი საშუალებებით ვერ ხერხდება, შეიძლება საჭირო გახდეს **Reset ან Reinstallation**. Reset Windows-ს ხელახლა აყენებს შესაბამისი პარამეტრების მიხედვით, ხოლო სრული Reinstallation ჩვეულებრივ გულისხმობს Windows-ის ახალი ინსტალაციის გაკეთებას. ასეთ დროს განსაკუთრებით მნიშვნელოვანია მომხმარებლის მონაცემების წინასწარ Backup-ი.

Backup-ის დაგეგმვისას ასევე უნდა განვსაზღვროთ **რა მონაცემების აღდგენა გვჭირდება და რამდენად სწრაფად**. მაგალითად, ჩვეულებრივი ფოტოების აღდგენა შეიძლება რამდენიმე საათს დაელოდოს, ხოლო კომპანიის მნიშვნელოვანი სერვერის გათიშვისას შეიძლება საჭირო იყოს სისტემის ძალიან სწრაფად დაბრუნება. აქედან გამომდინარე, Backup Strategy დამოკიდებულია მონაცემების მნიშვნელობაზე, აღდგენის დროზე და დასაშვებ მონაცემთა დაკარგვაზე.

ამასთან დაკავშირებულია ორი მნიშვნელოვანი ცნება: **RPO (Recovery Point Objective)** და **RTO (Recovery Time Objective)**. RPO განსაზღვრავს, მაქსიმუმ რამდენი დროის მონაცემების დაკარგვაა მისაღები. მაგალითად, თუ RPO არის 1 საათი, სისტემა ისე უნდა იყოს ორგანიზებული, რომ ავარიის შემთხვევაში დაახლოებით ბოლო ერთი საათის მონაცემებზე მეტი არ დაიკარგოს. RTO კი განსაზღვრავს, რამდენ ხანში უნდა აღდგეს სისტემა სამუშაო მდგომარეობაში.

საბოლოოდ, Backup და Recovery უნდა აღვიქვათ როგორც ერთი მთლიანობა. **Backup გვაძლევს მონაცემების დამატებით ასლს, ხოლო Recovery გვაძლევს ამ მონაცემებისა და სისტემის აღდგენის შესაძლებლობას.** კარგი ადმინისტრატორი არ ელოდება დისკის გაფუჭებას ან მონაცემების დაკარგვას — წინასწარ ქმნის Backup Strategy-ს, ამოწმებს Backup-ის სისწორეს და იცის, რა ნაბიჯებით უნდა აღადგინოს სისტემა პრობლემის შემთხვევაში.
